# 嵌入式项目开发流程规范（可复用）

> 这是一套可以直接复制到新工程的**嵌入式开发流程**，
> 与具体芯片、外设、行业无关：换一颗 MCU、换一个领域，规则仍然成立。
>
> 目标：让"一个人 + AI 协作"的嵌入式项目也能做到
> **每一步有方案、每一改有验证、每一个数字有出处、每一份文档不过期**。

---

## 0. 三十分钟起步

拿到一个新项目时，只做三件事：

```bash
# 1) 一条命令生成骨架（约 1 秒）
bash tools/new_project.sh my_project

# 2) 在生成的目录里跑一次自检（构建/测试没有就跳过）
cd my_project
bash test/verify.sh          # 期望 RESULT: PASS

# 3) 打开 STATUS.md，写下"下一步"的第一条
```

接下来按 `08_新工程落地清单.md` 逐项打钩即可。
生成的内容：`STATUS.md`、`README.md`、`docs/{00,01,19,38}`、`test/{doc_check.py,verify.sh}`、
`.gitattributes`、`.gitignore`——都不绑具体芯片与工具链。

> 骨架**不含**工程文件、启动代码、HAL：那部分按你的芯片与 IDE 建，
> 建完把它接进 `test/verify.sh` 第 3 步（固件构建）即可。

## 1. 这套流程解决什么问题

| 常见问题 | 本流程的对策 |
|---|---|
| 改完就烧，烧完就"好像可以了" | 三方验证门禁（构建 / 主机测试 / 文档检查） |
| 现象时好时坏，越改越乱 | 调试方法论：先仪表、后假设、对照实验 |
| 文档写着旧结论，代码早已改掉 | 文档检查工具 + 版本号绑定 |
| 需求一多就不知道做到哪了 | 阶段化推进 + 进度表 + 验收标准 |
| 换一个工程又要重新摸索一遍 | 本仓库整套复制，改 5 个地方即可 |

## 2. 十条硬规则（TL;DR）

1. **先方案，后动手**：任何非平凡改动先出方案，评审通过再执行。
2. **先仿真，后上板**：算法改动先在主机/WSL 上跑通，再进固件。
3. **一阶段一验收**：阶段不通过不进下一阶段，不跳步。
4. **三方验证才提交**：构建 0E/0W + 主机测试全过 + 文档检查通过。
5. **每次可烧录的改动都递增版本号**，文档里写的版本必须与代码一致。
6. **判据要用物理不变量**，不能用会随工况漂移的量（血的教训，见 `07`）。
7. **模式切换必须有硬优先级**，不能只靠"标志位"。
8. **先测量再修改**：没有数据支撑的修改都是猜测。
9. **保护只许加固，不许为了"跑通"而放宽**。
10. **硬件动作先请示**：烧录、接串口、断电、拆线都要先确认。

## 3. 目录结构

```
dev_workflow/
├── README.md                  ← 本文件：总览与使用方法
├── 01_开发流程总纲.md          ← 五个阶段与门禁
├── 02_文档体系规范.md          ← 必备文档清单、编号、写作规则
├── 03_阶段推进与验收.md        ← 阶段拆分方法、验收标准模板
├── 04_仿真先行.md              ← 主机仿真 / 离线算法 / 硬件在环 三级
├── 05_验证与提交规范.md        ← 三方验证、版本号、提交信息、分支
├── 06_硬件与安全约定.md        ← 授权模型、安全红线、保护测试方法
├── 07_调试方法论.md            ← 判据设计、对照实验、症状-根因表
├── 08_新工程落地清单.md        ← 从零搭建时按此清单逐项打钩
├── 09_通信与协议.md            ← 帧格式、状态机、超时、主机侧脚本
├── 10_资源预算.md              ← Flash/RAM/栈/CPU 怎么量、怎么留余量
├── 11_需求与方案.md            ← 需求写成可测量、方案对比、风险前置
├── tools/
│   ├── doc_check.py           ← 通用文档检查（复制到新工程 test/ 下）
│   └── new_project.sh         ← 一条命令生成新工程骨架
└── templates/                 ← 可直接复制的文档模板
    ├── t_STATUS.md            ← 一页纸状态牌（每天看的那一页）
    ├── t_开发日志条目.md
    ├── t_进度表.md
    ├── t_框架文档.md
    ├── t_阶段方案.md
    ├── t_阶段验收.md
    ├── t_已知问题与限制.md
    └── t_踩坑清单.md          ← 现象→根因→现在的规矩
```

> 八个模板对应四种"必须写"的场景：
> **开工前**写需求与方案（`t_阶段方案`，配合 `11`），**过程中**记日志、框架与状态（`t_开发日志条目`、`t_框架文档`、`t_STATUS`），
> **收尾时**做验收与归档（`t_阶段验收`、`t_进度表`、`t_已知问题与限制`），
> **任何时候**踩到坑就立刻进踩坑清单（`t_踩坑清单`）——它是个人开发者回报率最高的资产。

> **`t_STATUS.md` 是唯一每天要看的那一页**：做到哪 / 下一步 / 卡在哪 / 悬而未决。
> 超过一页就说明它变成了文档，而不是状态牌。

> **工具自带**：`tools/doc_check.py` 是通用版（乱码 / 表格结构 / 代码块配对 /
> 结尾换行 / CRLF / 重复标题），不依赖任何工程宏。复制到新工程的
> `test/doc_check.py` 后，再按 §4.2 第 1 项补上工程专属检查
> （版本号、帮助行数、波形通道数）。

## 4. 怎么复用到新工程

### 4.1 复制

最快的方式是跑一次脚手架，它会把下面这套目录结构直接生成出来：

```bash
bash tools/new_project.sh my_project
```

想要手工搭、或想看生成的是什么，就按下面的结构复制：

把本仓库整体复制到新工程根目录、改名 `workflow/`，然后把 `docs/` 建成下图结构：

```
新工程/
├── STATUS.md                   ← 一页纸状态牌（templates/t_STATUS.md）
├── docs/
│   ├── 00_开发日志.md          ← 追加式，永不删旧条目
│   ├── 01_项目进度.md          ← 唯一的"现在做到哪"的事实来源
│   ├── 10_框架_主框架.md
│   ├── 11_框架_<子系统>.md     ← 一个子系统一份，按 11,12,13… 编号
│   ├── 18_待确认清单.md        ← TBD 集中营
│   ├── 19_硬件资源与引脚映射.md ← 引脚、外设、时钟、中断优先级
│   ├── 30_命令手册.md          ← 交互式命令的完整说明
│   ├── 31_参数表.md            ← 所有可调参数的唯一出处
│   ├── 32_调试指南.md          ← 常见现象与排查路径
│   ├── 38_踩坑清单.md          ← 现象→根因→现在的规矩（templates/t_踩坑清单.md）
│   └── 90_已知问题与限制.md   ← 也可放在 30~39 段
├── test/
│   ├── doc_check.py            ← 文档一致性静态检查
│   ├── verify.sh               ← 一条命令跑完构建+测试+文档检查
│   ├── host/                   ← 主机仿真（fake HAL + 单元测试）
│   └── accept/                 ← 串口验收脚本（每阶段一个）
└── workflow/                   ← 本仓库复制过来后放在这里
```

> **`90_已知问题与限制` 的位置可以二选一**：`90`（推荐）或 `36`
> （放在 30~39 "使用文档" 段，适合已知问题很多、需要分类的工程）。
> 关键是**只存在一处**——两处都写必然分叉。

### 4.2 只改这 5 处

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `test/doc_check.py` | 从 `tools/doc_check.py` 复制，再补版本号正则、帮助行数/通道数等工程专属检查 |
| 2 | 框架文档编号段 | `10` 主框架，`11+` 子系统；按新工程划分 |
| 3 | `docs/01_项目进度.md` | 阶段划分（S0…Sn）与验收标准 |
| 4 | `05_验证与提交规范.md` §2 | 构建命令、测试命令、版本号宏名 |
| 5 | `workflow/templates/` | 模板里的占位符替换为新工程术语 |

其余内容可直接沿用。

## 5. 一个功能从想法到上板的完整轨迹

```
想法
 │
 ├─① 写进 docs/01 的"待做"         ← 需求入库，避免口头遗忘
 │
 ├─② 出方案（templates/t_阶段方案.md）
 │     · 目标 / 非目标
 │     · 技术路线与备选
 │     · 验证方法（怎么证明它成了）
 │     · 风险
 │     ↓ 评审通过
 │
 ├─③ 仿真验证（04_仿真先行）
 │     · 主机单元测试 / 离线 Python / 仿真波形
 │     ↓ 通过
 │
 ├─④ 固件实现 + 版本号 +1
 │
 ├─⑤ 三方验证（05_验证与提交规范）
 │     · 构建 0E/0W
 │     · 主机测试 N/N
 │     · doc_check PASS
 │     ↓ 全过
 │
 ├─⑥ 提交（一次逻辑改动一个提交，信息含"问题/根因/修法/验证"）
 │
 ├─⑦ 上板验证（06_硬件与安全约定：先请示）
 │     · 验收脚本 / 人工操作
 │     · 数据写入 docs/00 开发日志
 │     ↓ 达标
 │
 └─⑧ 更新 docs/01 进度表 + 相关框架文档 → 进入下一个功能
```

**任何一步失败，就回到上一步，不允许"带病前进"。**

## 6. 与"AI 协作"的约定

本流程假设执行者可能是 AI，因此额外要求：

| 约定 | 原因 |
|---|---|
| 方案必须写成文档，不接受口头 | AI 上下文会丢，文档不会 |
| 每个结论必须带数据（数值、日志片段） | 防止"看起来可以了"的幻觉 |
| 修改前必须先读代码/文档 | 防止重复发明、防止覆盖已有修复 |
| 硬件动作先请示 | 物理世界不可回滚 |
| 一次只改一个变量 | 否则失败时无法归因 |
| 假设被推翻时必须显式记录 | 这是最有价值的知识沉淀 |
| 文档与代码不一致时，先改文档再继续 | 否则后续所有推理都建立在错误前提上 |

## 7. 本规范的"最小可用版"

如果新工程很小（几百行、一次性验证），可只做四条：

1. `docs/00_开发日志.md` + `docs/01_项目进度.md`
2. 每次改动递增版本号
3. 提交前跑一遍构建 + 测试
4. 关键判据用物理不变量（见 `07`）

其余文档在工程变大、或需要第二个人接手时再补齐。
